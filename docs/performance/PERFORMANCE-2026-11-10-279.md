# 0.2.79: отчёт пользователя и пассивная запись

Исходный отчёт: CherryPick_report_2026-11-10_18-02-26-237.zip, модуль 0.2.78, PLZ110/API37, launcher 17.5.4. APK в отчёте не устанавливался. Исходные файлы распакованы только локально в E:/COSMOD/scratch/audit279.

Пользователь уточнил: заметный лаг появляется при обычном использовании после завершения работы агента. Короткие автоматизированные циклы не считаются воспроизведением этого сценария. После уточнения ввод на устройстве прекращён.

## Подтверждённая ошибка

FrameJank имел общий last/windowStart/ArrayList для всех Choreographer.doFrame в процессе. В отчёте одни и те же окна публикуются из UI 24832 и потока 25110 с разными frames; интервал смешивает независимые Choreographer. Сортировка и String.format выполнялись на вызывающем потоке; GlassLogger.i синхронно вызывал XposedBridge.log. Такой счётчик не показывает реальные пропуски отображения и создаёт лишнюю работу в том числе в UI.

Хук и класс удалены. Причинная связь с субъективным лагом не доказана, исправление всего лага не заявляется.

## Пассивный путь

Только системный источник android.surfaceflinger.frametimeline, RAM ring 16 МиБ, 30 минут максимум. Без sched_switch, atrace, видео, скриншотов, запуска приложений и касаний. Запись запускается явно внешним ADB-инструментом, не приложением и не при старте лаунчера. Нулевая стоимость не утверждается.

На этой прошивке CloneSession IPC и detach/attach не работают. Использован обычный background-wait клиент; при отчёте проверяются числовой PID и точная строка конфига в /proc/PID/cmdline, затем SIGINT штатно завершает только этот recorder. Чтение файла начинается после завершения процесса. Старые трассы при отсутствующем процессе не добавляются. Создание ZIP и остановка выполняются вне UI.

Первичная проверка записи без ввода дала валидную трассу 1,21 МБ и 3847 записей actual_frame_timeline_slice. Это проверка сбора, не воспроизведение пользовательского лага; общее число jank по всем слоям не трактуется как пропуски лаунчера.

## Статус

Устранён мешающий диагностический хук; причина остаточного лага остаётся открытой. Следующий пользовательский ZIP во время включённой пассивной сессии должен содержать системную трассу. Сопоставлять нужно actual/expected FrameTimeline слоя лаунчера и iconViewSurface, учитывая общие display-frame токены, а не складывать события разных слоёв.


Итог: 0.2.79 установлена без запуска экранов и автоматического ввода, выполнен один перезапуск процесса лаунчера для снятия старого хука. 71 unit-тест, assembleRelease и lintRelease прошли. Изолированная проверка app_process вызвала реальную PassiveFrameTrace.snapshot: recorder завершился, файл записался; повторный вызов без recorder вернул null и не использовал старый файл. Настройки не менялись относительно окончания .278.

После проверок включена новая 30-минутная сессия для обычного использования. Лаг не объявлен устранённым; ожидаются данные реального проявления. Автоматическая сессия .278-report-baseline до уточнения пользователя не считается воспроизведением и не используется для вывода об устранении лага.
